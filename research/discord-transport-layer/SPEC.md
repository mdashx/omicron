# Pi Discord Transport Layer

## Intent

Add a startup-loaded Discord transport layer to Pi so Discord messages, reactions, and lifecycle events are normalized into agent-friendly events, and agent outputs are turned back into Discord replies, reactions, and thread actions.

This must be enforced by runtime wiring, not by prompting the model to remember how to talk to Discord.

---

## 1. `DiscordTransportDefaults` and `DiscordTransportConfig`

### Prose Spec

Pi should ship with a built-in default Discord transport configuration for local development and controlled deployments.

The user may override any part of it with config or environment variables, but a working token source, sensible allowlists, and idempotency state should exist even when the user does very little.

### Z Spec

```text
DiscordTransportDefaults
  enabled: 𝔹
  tokenSource: seq CHAR
  commandPrefix: seq CHAR
  guildAllowlist: ℙ seq CHAR
  channelAllowlist: ℙ seq CHAR
  dryRun: 𝔹
  statePath: seq CHAR
  failClosed: 𝔹
where
  enabled = true
  tokenSource ≠ ⟨⟩
  commandPrefix ≠ ⟨⟩
  statePath ≠ ⟨⟩
  failClosed = true

DiscordTransportConfig
  enabled?: 𝔹
  tokenSource?: seq CHAR
  commandPrefix?: seq CHAR
  guildAllowlist?: ℙ seq CHAR
  channelAllowlist?: ℙ seq CHAR
  ownerAllowlist?: ℙ seq CHAR
  dryRun?: 𝔹
  statePath?: seq CHAR
  threadMode?: seq CHAR
  replyMode?: seq CHAR
  maxActionsPerTurn?: ℕ

ResolvedDiscordTransportConfig
  enabled: 𝔹
  tokenSource: seq CHAR
  commandPrefix: seq CHAR
  guildAllowlist: ℙ seq CHAR
  channelAllowlist: ℙ seq CHAR
  ownerAllowlist: ℙ seq CHAR
  dryRun: 𝔹
  statePath: seq CHAR
  threadMode: seq CHAR
  replyMode: seq CHAR
  maxActionsPerTurn: ℕ
where
  enabled = true
  tokenSource ≠ ⟨⟩
  commandPrefix ≠ ⟨⟩
  statePath ≠ ⟨⟩
  maxActionsPerTurn > 0
```

### Data examples

Default config:

```json
{
  "enabled": true,
  "tokenSource": "env.DISCORD_BOT_TOKEN",
  "commandPrefix": "!",
  "guildAllowlist": ["123456789012345678"],
  "channelAllowlist": ["234567890123456789"],
  "ownerAllowlist": [],
  "dryRun": true,
  "statePath": "~/.pi/discord-transport/state.json",
  "threadMode": "off",
  "replyMode": "reply-to-message",
  "maxActionsPerTurn": 8
}
```

User overrides:

```json
{
  "dryRun": false,
  "channelAllowlist": ["234567890123456789", "345678901234567890"],
  "replyMode": "mention-only"
}
```

### Implementation suggestions / specifics

- Load config during Pi startup before the agent loop begins.
- Merge user overrides onto built-in defaults.
- Keep the Discord token out of prompts and out of git.
- Create the state directory recursively if needed.
- Keep `dryRun` as a first-class toggle.
- Default to deny-by-default scope checks.

## 2. `DiscordSessionEnvelope`

### Prose Spec

`DiscordSessionEnvelope` identifies one Pi runtime session and carries the metadata that applies to every Discord event in that session.

The session ID must be generated by Pi at runtime, not by the model.

### Z Spec

```text
DiscordSessionEnvelope
  sessionId: seq CHAR
  startedAt: seq CHAR
  source: seq CHAR
  host: seq CHAR
  runtimeVersion: seq CHAR
  packageVersion: seq CHAR
  botUserId: seq CHAR
  applicationId: seq CHAR
  transportMode: seq CHAR
where
  sessionId ≠ ⟨⟩
  startedAt ≠ ⟨⟩
  source ≠ ⟨⟩
```

### Data examples

```json
{
  "sessionId": "2026-06-05T19:45:12Z_8f3a",
  "startedAt": "2026-06-05T19:45:12Z",
  "source": "pi-discord-transport",
  "host": "easter-laptop",
  "runtimeVersion": "2026.6.5",
  "packageVersion": "0.1.0",
  "botUserId": "234567890123456789",
  "applicationId": "123456789012345678",
  "transportMode": "gateway"
}
```

### Implementation suggestions / specifics

- Generate the session ID at startup using timestamp plus a short random suffix.
- Capture runtime metadata from Pi itself, not from the model.
- Keep the envelope immutable for the rest of the session.
- Emit a `ready`/`session_start`-style transport event after connection.

## 3. `DiscordInboundEvent`

### Prose Spec

`DiscordInboundEvent` is the normalized shape of anything the transport layer receives from Discord that may matter to the agent.

The transport should convert Discord-specific gateway payloads into this stable internal form before doing any higher-level planning.

### Z Spec

```text
EVENTTYPE ::= ready | messageCreate | reactionAdd | error | heartbeat

DiscordInboundEvent
  eventId: seq CHAR
  eventType: EVENTTYPE
  guildId: seq CHAR
  channelId: seq CHAR
  messageId: seq CHAR
  authorId: seq CHAR
  content: seq CHAR
  createdAt: seq CHAR
  jumpUrl: seq CHAR
  rawKind: seq CHAR
where
  eventId ≠ ⟨⟩
  eventType ≠ ⟨⟩
```

### Data examples

```json
{
  "eventId": "evt_01JABC...",
  "eventType": "messageCreate",
  "guildId": "345678901234567890",
  "channelId": "456789012345678901",
  "messageId": "678901234567890123",
  "authorId": "789012345678901234",
  "content": "!status",
  "createdAt": "2026-06-05T18:21:00Z",
  "jumpUrl": "https://discord.com/channels/...",
  "rawKind": "gateway.messageCreate"
}
```

### Implementation suggestions / specifics

- Normalize gateway events immediately on receipt.
- Keep only the fields the harness actually needs.
- Preserve raw payloads only in debug logs, not as the primary state model.
- Treat `ready` as a lifecycle event, not a user action.

## 4. `DiscordDirective`

### Prose Spec

`DiscordDirective` is the parsed command or intent extracted from an inbound Discord message.

In the simplest harness, directives can be small: ping, status, echo, react, or ignore.

### Z Spec

```text
DIRECTIVETYPE ::= ping | status | echo | react | ignore

DiscordDirective
  directiveType: DIRECTIVETYPE
  sourceEventId: seq CHAR
  targetChannelId: seq CHAR
  argumentText: seq CHAR
where
  sourceEventId ≠ ⟨⟩
```

### Data examples

```json
{
  "directiveType": "echo",
  "sourceEventId": "evt_01JABC...",
  "targetChannelId": "456789012345678901",
  "argumentText": "hello world"
}
```

### Implementation suggestions / specifics

- Parse a tiny command grammar first.
- Recommended grammar: `!ping`, `!status`, `!echo <text>`, `!react <emoji>`.
- If a message does not match the prefix, return `ignore`.
- Keep parsing deterministic and boring.

## 5. `DiscordActionPlan`

### Prose Spec

`DiscordActionPlan` is the internal result of handling a directive.

It describes what the transport should do through the Discord API: reply, react, open a thread, log only, or do nothing.

### Z Spec

```text
ACTIONTYPE ::= reply | addReaction | openThread | logOnly | noOp

DiscordActionPlan
  actionId: seq CHAR
  sourceEventId: seq CHAR
  actionType: ACTIONTYPE
  targetChannelId: seq CHAR
  targetMessageId: seq CHAR
  bodyText: seq CHAR
  emoji: seq CHAR
where
  actionId ≠ ⟨⟩
```

### Data examples

```json
{
  "actionId": "act_01JABC...",
  "sourceEventId": "evt_01JABC...",
  "actionType": "reply",
  "targetChannelId": "456789012345678901",
  "targetMessageId": "678901234567890123",
  "bodyText": "pong",
  "emoji": ""
}
```

### Implementation suggestions / specifics

- Make the action plan a pure data object.
- Separate planning from execution.
- `dryRun` should print the plan instead of sending it.
- For `reply`, use the bot API helper for message creation.
- For `addReaction`, only use configured emoji values.

## 6. `DiscordTransportState`

### Prose Spec

`DiscordTransportState` stores the minimum memory needed for idempotency and restart safety.

The transport should remember which Discord events it has already handled, plus basic lifecycle metadata.

### Z Spec

```text
DiscordTransportState
  lastReadyAt: seq CHAR
  lastHeartbeatAt: seq CHAR
  processedEventIds: ℙ seq CHAR
  processedActionIds: ℙ seq CHAR
  lastSeenByChannel: seq CHAR
where
  processedEventIds = ∅ ∨ processedActionIds = ∅ ∨ lastReadyAt ≠ ⟨⟩
```

### Data examples

```json
{
  "lastReadyAt": "2026-06-05T18:20:15Z",
  "lastHeartbeatAt": "2026-06-05T18:21:00Z",
  "processedEventIds": ["evt_01JABC..."],
  "processedActionIds": ["act_01JABC..."],
  "lastSeenByChannel": "{\"456789012345678901\":\"678901234567890123\"}"
}
```

### Implementation suggestions / specifics

- Store state in a small JSON file first.
- Deduplicate on `eventId` before planning actions.
- Append/update state after successful action execution.
- Keep a heartbeat timestamp so the process is visibly alive.

## 7. `DiscordTransportRunLoop`

### Prose Spec

`DiscordTransportRunLoop` is the end-to-end process: connect, receive events, scope-check, normalize, parse, plan, execute, persist.

This is the smallest reliable Discord transport layer.

### Z Spec

```text
DiscordTransportRunLoop
  config: ResolvedDiscordTransportConfig
  state: DiscordTransportState
  event: DiscordInboundEvent
  directive: DiscordDirective
  actionPlan: DiscordActionPlan
where
  event.eventId ∉ state.processedEventIds
  event.guildId ∈ config.guildAllowlist
  event.channelId ∈ config.channelAllowlist
```

### Data examples

```json
{
  "sequence": [
    "connect",
    "ready",
    "receive event",
    "scope check",
    "parse directive",
    "create action plan",
    "execute action",
    "persist state"
  ]
}
```

### Implementation suggestions / specifics

- Use a single process at first.
- Keep one event queue and one action executor.
- Log each stage clearly.
- Start with one command channel and one reply path.
- Add richer agent behavior only after the skeleton is stable.

## 8. `DiscordTransportEnforcement`

### Prose Spec

`DiscordTransportEnforcement` describes the runtime guarantees that make Discord transport mandatory and independent of LLM behavior.

Pi should wire the transport into startup, event hooks, and shutdown. The model should never be the source of truth for whether Discord messages are handled.

### Z Spec

```text
DiscordTransportEnforcement
  pluginLoaded: 𝔹
  hooksInstalled: 𝔹
  schemaValidated: 𝔹
  startupBlockedIfMissing: 𝔹
  llmInPath: 𝔹
where
  pluginLoaded = true
  hooksInstalled = true
  schemaValidated = true
  startupBlockedIfMissing = true
  llmInPath = false
```

### Data examples

```json
{
  "pluginLoaded": true,
  "hooksInstalled": true,
  "schemaValidated": true,
  "startupBlockedIfMissing": true,
  "llmInPath": false
}
```

### Implementation suggestions / specifics

- Load the transport plugin before the agent loop starts.
- Register hooks for inbound events, outbound actions, and shutdown.
- Validate records before they reach the executor.
- Fail startup if transport wiring is enabled but unavailable.
- Keep all transport decisions in runtime code, not in prompts or model output.

---

## Suggested first milestone

Pi can start with default Discord transport settings, connect with a bot token, accept only allowlisted guild/channel messages, normalize inbound events, parse a small prefix command set, emit deterministic action plans, send or dry-run replies/reactions, persist processed event IDs, and shut down cleanly without duplicate replies.
